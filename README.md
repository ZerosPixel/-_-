# БУНКЕР — браузерная многопользовательская игра

Существующий проект на HTML, CSS и JavaScript; сборка и npm не требуются. Это доработанная версия исходного `bunker-lite-ui-redesign.zip`, а не переписанный с нуля прототип. Исходные восемь локальных иллюстраций катастроф сохранены.

## Файлы проекта

- `index.html` — стартовая HTML-страница и подключения локальных ресурсов / PeerJS CDN.
- `styles.css` — оформление и адаптивная раскладка.
- `app.js` — правила, авторитетное состояние комнаты у хоста, клиентский протокол, приватность карточек, раунды, голосование, катастрофы, текстовая сводка рисков/запасов/инфраструктуры, состояние бункера и финальный расчёт.
- `assets/` — восемь локальных изображений катастроф.
- `tests/browser_regression.py` — браузерная регрессия на Chromium/Playwright.
- `tests/TEST_RESULTS.json` — последний результат браузерной регрессии.
- `tests/host_tools_regression.cjs` и `tests/HOST_TOOLS_RESULTS.json` — тесты инструментов хоста и финальных проблем бункера.
- `PROJECT_STATUS.md` — журнал этапов, найденных дефектов и ограничений проверки.
- `BUNKER_CHANGELOG.md` — краткий список последних изменений по финальным проблемам, ботам и соединению.
- `REQUIREMENTS_TRACEABILITY.md` — таблица трассировки требований ТЗ §0–58 и §2A к коду и проверкам.
- `docs/specification/` — приложенные полные текстовая и Markdown-копии ТЗ и стартовой инструкции.

## Правила и ограничения

- В комнате должны быть **6–15 реальных участников**. Пустые фиктивные слоты не создаются. При 6 игроках вместимость бункера равна 3; далее применяется существующее правило расчёта.
- Создатель комнаты остаётся участником партии, но его вкладка браузера выполняет техническую роль авторитетного хоста для синхронизации. Добавлены повторное подключение сигнализации и запрос актуального состояния после возвращения вкладки. В лобби доступно необязательное удержание экрана включённым; оно помогает только пока браузер активен.
- Клиенты восстанавливают прежнего участника по сохранённому `clientId`, пока состояние комнаты и браузер хоста существуют. Очистка локальных данных или закрытие хоста не эквивалентны серверному постоянному хранению.
- В игре есть 22 структурированных сценария катастроф и 34 уникальных события бункера. Информация открывается постепенно, последствия катастрофы и актуальные запасы описываются текстом прямо под иллюстрацией сценария; плитки числовых метрик и полосы `/100` удалены. Эффекты событий учитываются в текущем состоянии и финальном расчёте. Проблемы бункера автоматически оцениваются в финале по профессиям оставшихся игроков; отдельной кнопки ремонта нет. Например, кладовщик или фасовщик может спасти продукты с повреждённой упаковкой, фармацевт — проверить сомнительные лекарства, лингвист или учитель английского — перевести незнакомые инструкции.
- Закрытые карты других игроков, идентификаторы соединений и план будущих событий не должны передаваться в клиентском снимке как открытые данные.
- PeerJS подключается с внешнего CDN (`unpkg.com`); для реальных P2P-сессий нужны доступ к CDN и доступная сеть WebRTC. Android/iOS могут приостанавливать JavaScript и WebRTC в фоновой вкладке; клиентский код не может гарантировать непрерывную связь при переключении в Telegram. Для устойчивой фоновой работы нужен отдельный постоянно работающий сервер/relay. Текущий набор локальных браузерных проверок **не** подтверждает работу реальной сети, Android или iOS.


## Инструменты хоста для тестирования

В своей комнате до старта партии хост может нажать **«Заполнить до 6»**, чтобы добавить пять тестовых ботов к себе, либо добавлять ботов по одному. Тестовые боты получают обычные карты персонажей и участвуют в игровых правилах, но не подключаются отдельными устройствами.

Во время ходов кнопка **«Завершить ход · открыть 2 случайные»** раскрывает до двух случайных ещё скрытых характеристик текущего игрока и передаёт ход дальше. Во время голосования можно выбрать голос каждого бота вручную или нажать **«Случайные голоса ботов»**. В панели хоста есть возможность удалить не-хоста; если кандидат удалён во время защиты, игра переходит к повторному голосованию, а не должна зависать.

Боты — средство прогнать этапы и проверить исходы, а не полноценные стратегические соперники: их случайные голоса не моделируют человеческое поведение. На финальном экране проблемы бункера автоматически решаются, если среди невыбывших персонажей есть подходящая профессия; иначе проблема остаётся в отчёте и снижает устойчивость.

На стартовом экране пять этапов выстроены в одну строку, включая узкую мобильную ширину.

## Запуск локально

Требуются Python 3 и обычный браузер.

```bash
python -m http.server 8000
```

Откройте `http://localhost:8000`. Для игры с других устройств нужен общедоступный HTTPS-адрес; `localhost` на телефоне указывает на сам телефон, а не на компьютер.

## GitHub Pages

1. Загрузите содержимое корня проекта в корень репозитория, сохранив `assets/`.
2. В репозитории откройте **Settings → Pages**.
3. Включите публикацию из нужной ветки и каталога `/ (root)`.
4. Проверьте опубликованный адрес с нескольких реальных устройств. Размещение не считается сетевым тестом само по себе.

Пути локальных CSS/JS относительные, поэтому подходят для публикации из корня проекта или каталога проекта GitHub Pages.

## Тесты

Основная доступная регрессия запускается так:

```bash
python tests/browser_regression.py
```

Для окружения, где Playwright ещё не установлен:

```bash
python -m pip install playwright
python -m playwright install chromium
```

Сценарии исполняются в Chromium с реальным DOM и JavaScript, но состояние участников и сетевые сообщения в них создаются тестом — внешний PeerJS-сервер и сеть не задействованы. Смотрите `tests/TEST_RESULTS.json` для списка браузерных проверок и `tests/HOST_TOOLS_RESULTS.json` для проверок ботов/финальных проблем. Второй набор запускается через `node tests/host_tools_regression.cjs`.

## Техническая модель

Авторитетное состояние живёт в вкладке хоста. Снимки имеют возрастающий `stateSeq`; клиент игнорирует устаревшие снимки и подтверждает применённые. Хост связывает разрешённые действия с участником, назначенным соединению, а не доверяет переданному клиентом `voterId`. Это не заменяет серверную авторизацию: хост и PeerJS остаются клиентской P2P-архитектурой без отдельного backend.


## Дополнительные обновления

- Финал упрощён: крупный зелёный/красный исход и короткое объяснение; необязательные подробности открываются отдельно.

- Текущий прогон: 26/26 браузерных тестов, 26/26 тестов хоста/логики. Реальная сеть PeerJS/WebRTC и тестирование на телефонах не подтверждены.


## Сэмпловая проверка разнообразия исходов (seed 20261009)

Запущена воспроизводимая симуляция `tests/final_outcome_simulation.cjs`: 500 случайно сгенерированных составов из шести персонажей, три из которых попадают в бункер; вентиляция и санитария установлены на средний уровень. В этом контрольном наборе 314 партий закончились выживанием и 186 — гибелью; 140 завершились неконтролируемой инфекционной угрозой, а в 109 случаях заразное состояние было сдержано. Это подтверждает наличие обеих ветвей исхода в выбранном наборе, но не является полной балансировкой игры для всех бункеров, размеров лобби и порядков раскрытия. Результат сохранён в `tests/FINAL_OUTCOME_SIMULATION.json`.


## Текстовый обзор катастрофы

Под изображением и названием сценария интерфейс объясняет, какие системы и ресурсы оказываются под давлением, каковы текущие запасы бункера и в каком состоянии его инфраструктура. Значения не разложены по таблице плиток и полосам прогресса: они вписаны в предложения, а состояние обновляется вслед за игровыми событиями. Характеристики персонажей выбираются случайно независимо по каждой категории; карты факта не назначают человеку фиксированную профессию.
